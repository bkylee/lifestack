# Azure Database for PostgreSQL Flexible Server

## What it is

Azure-managed PostgreSQL running on a customer-controlled VM under a managed service envelope. "Flexible Server" is the second-generation PaaS Postgres offering (replaces "Single Server"), and the only one that supports VNet integration via subnet delegation — i.e. Postgres lands a NIC with a private IP **directly in your VNet**, with no Private Endpoint indirection.

Sits in the **data tier** of the architecture. Stores everything persistent: users, hobbies, products, attributes, ownerships, reviews, scores, follows.

## Why we use it

- **Don't run a database.** Backups, patching, OS upgrades, HA failover (when enabled), monitoring hooks — all managed by Azure. Operational burden is small relative to a self-hosted Postgres on a VM.
- **Cheapest tier is cheap.** `B_Standard_B1ms` (Burstable, 1 vCore, 2 GiB) is ~$13/month compute + ~$4/month for 32 GB storage. Postgres backups are free up to the provisioned storage size for the chosen retention window.
- **Native VNet integration.** Delegated-subnet mode means the server is on `10.10.2.0/24` with a real private IP, never exposed to the public internet. No Private Endpoint pricing surcharge for the connection.
- **`pgvector` ready.** The `vector` extension is on Azure's allowlist, allowlisted server-side here, and waiting for v3 taste-twin features. No need to switch databases or services later.
- **Standard Postgres protocol.** Prisma, `psql`, `pg_dump`, every Postgres tool — all just work. No lock-in to provider-specific drivers or APIs.

## How it's configured here

**Server:** `psql-lifestack-prod` in `rg-lifestack-data-prod`, region `eastus2`, availability zone `1`.

| Setting | Value | Why |
|---|---|---|
| Postgres version | `16` | Matches the local Docker dev environment; Postgres 16 is current GA on Azure. |
| SKU | `B_Standard_B1ms` (Burstable, 1 vCore, 2 GiB) | Cheapest line. Burstable bursts to baseline on demand; sufficient for v1 traffic. |
| Storage | `32 GB` Standard SSD | Postgres Flex's documented minimum. Auto-grow disabled to keep cost predictable. |
| Backup retention | `14 days` | Free up to provisioned storage size. Generous window for "oh no I dropped a table" recovery. |
| Geo-redundant backup | `disabled` | Saves cost. Region-pair failover is a v2 concern; for v1 a single-region full restore is enough. |
| HA (zone-redundant) | `disabled` | Would double compute cost. v1 traffic doesn't justify it. |
| Availability zone | `1` | Pinning to a fixed zone keeps the server's physical location predictable across applies. Required when HA is disabled (otherwise Azure picks for you). |
| Maintenance window | Sunday 02:00 UTC | Avoids weekday traffic. UTC because Azure's scheduler is UTC. |
| Public network access | **disabled** | Never reachable from the public internet. |
| Delegated subnet | `snet-pg-prod` (`10.10.2.0/24`) | VNet integration. Postgres lands a NIC at `10.10.2.4` directly in this subnet. |
| Private DNS zone | `privatelink.postgres.database.azure.com` | A record auto-registers on server creation. From inside the VNet, the public FQDN resolves to the private IP. |

**Database:** `lifestack`, UTF8 / `en_US.utf8`. One database; multiple schemas live inside it.

**Admin user:** `psqladmin`, password generated by Terraform (`random_password`, 32 chars, URL-safe). Persisted in the encrypted Terraform state today; migrating to Key Vault in a later step so the app reads via managed identity.

**Extensions allowlist (`azure.extensions`):** `vector`. Allowlisting is server-level; `CREATE EXTENSION vector;` is still required inside the `lifestack` database before pgvector types can be used.

**Files:**

- `infra/modules/postgres/` — reusable module (versions, variables, main, outputs).
- `infra/environments/prod/postgres.tf` — module invocation.
- `infra/environments/prod/outputs.tf` — `postgres_fqdn`, `postgres_database_name`, `postgres_admin_username`, `postgres_admin_password` (sensitive), `postgres_connection_string` (sensitive).

## Mental model

- **The server is a VM with a NIC in your VNet.** Not a service behind a load balancer. The private IP belongs to the delegated subnet; the FQDN resolves to it via the linked private DNS zone. From the app's perspective it's just `postgres://psqladmin:...@psql-lifestack-prod.postgres.database.azure.com:5432/lifestack?sslmode=require`.
- **Two layers of access control.** Network reachability (delegated subnet membership + NSG rules) and database-level auth (Postgres role/password, eventually AAD auth). Both must allow the connection.
- **Backups are storage-volume snapshots.** Restore creates a *new* server from a point-in-time snapshot of the storage volume. You don't restore in place — you restore alongside, swap the connection string, then retire the old server.

## Alternatives considered

- **Self-hosted Postgres on a Container Apps sidecar or a VM.** Maximum control, cheapest in pure resource cost, but you own backups, patching, OS upgrades, HA, monitoring, and zero-downtime version upgrades. The operational learning value of this exists, but the bridge-to-production goal is better served by knowing how to operate a managed service — that's what 90% of cloud architects actually run.
- **Azure Cosmos DB for PostgreSQL** (Citus). Sharded, distributed Postgres. Massive overkill for v1; minimum SKU is also ~5× the cost.
- **Azure Postgres Single Server.** Older generation, no VNet integration, being deprecated. No reason to start there in 2026.
- **Supabase / Neon.** Hosted Postgres on top of Azure / AWS. Cheaper at idle, but a different operational model (their console, their dashboard, their billing). The whole point here is to learn Azure's primitives. Defer.
- **PlanetScale / DynamoDB / Mongo.** Not Postgres. Loses everything below — typed Prisma, pgvector, `Prisma.sql`, FTS, JSON operators. Not on the table.

ADR-0009 captures the choice in formal form.

## Common operations

**Connect from inside the VNet** (when ACA is wired up):
```bash
psql "$(terraform -chdir=infra/environments/prod output -raw postgres_connection_string)"
```

**Read the connection string** (for one-off debugging from a jumpbox or peered network):
```bash
terraform -chdir=infra/environments/prod output -raw postgres_connection_string
```

**Run a migration** (will happen from CI / from a one-shot job inside the VNet):
```bash
DATABASE_URL="$(terraform -chdir=infra/environments/prod output -raw postgres_connection_string)" pnpm db:migrate
```

**Enable an allowlisted extension inside the database** (one-time, after allowlist update):
```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

**Add a new extension to the allowlist** — edit `extensions_allowlist` in `infra/environments/prod/postgres.tf` (comma-separated lowercase), then `terraform apply`. The server reloads its config (~30s, no downtime).

**Rotate the admin password** — `terraform taint module.postgres.random_password.admin && terraform apply`. This regenerates the password and pushes the new value to the server. Then re-publish to Key Vault (later step's procedure).

**Trigger a manual backup** — backups are automatic and continuous; no manual trigger exists. Point-in-time restore is the recovery primitive.

**Point-in-time restore** — `az postgres flexible-server restore --source-server psql-lifestack-prod --name psql-lifestack-prod-restore-YYYYMMDD --restore-time '...'`. Creates a new server; you then cut traffic over by changing the connection string.

**Stop the server** (to save money during long idle periods) — `az postgres flexible-server stop --resource-group rg-lifestack-data-prod --name psql-lifestack-prod`. Server stays stopped for up to 7 days, then Azure auto-starts it. Compute billing stops; storage billing continues.

## Gotchas

- **`vector` extension is lowercase.** The allowlist accepts `vector`, not `PGVECTOR`. Hit this on first apply. The portal's UI sometimes shows extension names uppercase but the parameter value is the lowercase canonical name. Error message lists all valid names.
- **Delegated subnet locks you in.** Once a Postgres Flex server is in a delegated subnet, you can't move it to a different subnet or VNet. Migration = restore-to-new-server. Pick your subnet on day one.
- **Region must match the VNet.** Postgres Flex with VNet integration requires the delegated subnet's VNet to be in the same region as the server. Cross-region VNet integration isn't supported.
- **`LocationIsOfferRestricted` in some regions.** Pay-as-you-go subscriptions are commonly blocked from provisioning Postgres Flex in `eastus`, `westus`, and other heavily-loaded regions. The fix is to pick a different region (`eastus2`, `westus2`, `westus3`). Hit this on initial deployment — moved everything from `eastus` to `eastus2`.
- **AZ pinning matters with HA disabled.** If you don't specify `zone`, Azure picks one on first create — and you'll get a noisy diff every plan because the API now returns a value that wasn't in your config.
- **`azurerm_postgresql_flexible_server_database` and `_configuration` apply *after* the server is `Ready`.** The server alone takes ~8 minutes to provision. The database and config resources serialize behind it.
- **Stopped servers auto-start after 7 days.** Stopping a server doesn't put it on ice indefinitely — Azure will turn it back on. This is a forced freshness check (so you don't accumulate stopped servers with security patches deferred indefinitely).
- **The admin password isn't stored anywhere except Terraform state.** Until we wire Key Vault, retrieve it with `terraform output -raw postgres_admin_password`. Don't try to set it in the portal — Azure overwrites it on the next `terraform apply`.

## Cost characteristics

| Component | Idle (v1) | What drives it |
|---|---|---|
| Compute (B_Standard_B1ms) | ~$13/mo | Always-on. ~$0 if stopped, but stops max out at 7 days. |
| Storage (32 GB Standard SSD) | ~$4/mo | Provisioned, not consumed. |
| Backups (14-day retention) | $0 | Free up to provisioned storage size. |
| Geo-redundant backups | $0 | Disabled. |
| **Total v1** | **~$17/mo** | |

**Scale-up triggers (v2+):**
- Burstable credits running out → upgrade to `GP_Standard_D2s_v3` (~$120/mo, 2 vCore, 8 GiB) for steady CPU.
- Storage approaching 80% of provisioned → bump `storage_mb`. Auto-grow stays off; intentional.
- p95 query latency degrading after the dataset grows → review `pg_stat_statements`, consider a read replica or a larger SKU before sharding.
