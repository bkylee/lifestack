# ADR-0009: Azure-managed Postgres Flexible Server (not self-hosted)

## Status

Accepted — 2026-05-10.

## Context

Lifestack needs a relational database for v1. The schema is non-trivial (users, hobbies, products, EAV attributes, ownerships, reviews, scored review dimensions, follows) and the access patterns are typical OLTP: row-level reads, scoped writes, joins across 2–4 tables. Future v3 features require vector similarity search (`pgvector`).

Constraints:

- **Budget cap of $100/month** across all of Azure (see budget guardrail in `infra/environments/prod/budget.tf`). Database can't dominate the bill.
- **Single operator** (me). Operational burden of managing a database myself competes with time spent on app code and learning higher-tier Azure services.
- **Cloud-architect learning goal.** I want to *operate* a managed service end-to-end — backups, restores, scaling, observability — not babysit a VM.
- **Network isolation.** Database must never be reachable from the public internet.
- **v3 vector search.** Whatever I pick must support `pgvector` natively, without bolting on a separate vector store.

## Decision

Use **Azure Database for PostgreSQL Flexible Server** in the **Burstable B1ms** SKU with **VNet integration via delegated subnet** (not Private Endpoint), in `eastus2`. Public network access disabled. 14-day backups, no geo-redundancy, no HA in v1.

`pgvector` allowlisted server-side via `azure.extensions = "vector"`; `CREATE EXTENSION vector;` runs against the `lifestack` database when v3 schema lands.

## Consequences

**What this enables:**

- Standard Postgres tooling (Prisma, `psql`, `pg_dump`, every Postgres driver) just works.
- pgvector is one `CREATE EXTENSION` away.
- Backups, patching, OS upgrades, monitoring hooks are Azure's problem.
- Restore is point-in-time within the 14-day window.
- VNet integration means the database is unreachable from the public internet from day one — defense in depth without extra cost.

**What this forecloses:**

- Cross-region or cross-VNet moves require restore-to-new-server. The delegated subnet relationship is sticky.
- Some Postgres extensions Azure hasn't allowlisted (e.g., niche FDWs, `pg_partman` is allowed but some less-common ones aren't) — if we need one of those later, it's a service-level escalation.
- HA failover, read replicas, and SKU changes happen on Azure's schedule, not ours.

**Operational burden:**

- Monthly: confirm backup verification (until automated), review slow-query log, watch SKU CPU credits.
- On schema changes: hand-reviewed migrations applied via CI against the actual production database — no auto-apply on destructive changes (per CLAUDE.md).
- On password rotation: `terraform taint module.postgres.random_password.admin && terraform apply`, then re-push to Key Vault.

**New risks:**

- Burstable SKU can exhaust CPU credits under sustained load. Trigger to escalate: p95 latency climbing or `pg_stat_statements` showing extended waits. Escalation path is documented in the service doc.
- Stopped servers auto-start after 7 days. Don't rely on stop-as-cost-control for indefinite idle periods.
- Storage doesn't auto-grow (off intentionally for cost predictability). Need to manually bump `storage_mb` before hitting 80%.

## Alternatives considered

**Self-hosted Postgres on a VM or Container Apps sidecar.** Cheapest in pure compute cost, maximum control. Rejected because (a) I want to learn how to operate a managed PaaS service, not how to babysit a VM with Postgres on it — the bridge-to-production gap is closed faster by the former; (b) backups, patching, and HA become my problem; (c) cost savings are marginal once you account for the time required.

**Azure Cosmos DB for PostgreSQL (Citus).** Sharded distributed Postgres. Minimum SKU ~5× the Burstable cost, and complexity is justified only when a single Postgres node demonstrably can't handle load. Lifestack at v1 scale fits in a single Postgres node by several orders of magnitude.

**Azure Postgres Single Server.** Older generation. No VNet integration (only Private Endpoint with extra cost). Being deprecated. No reason to start there in 2026.

**Supabase / Neon (hosted Postgres on top of Azure or AWS).** Cheaper at idle (free tiers). Different operational model — their console, their backup model, their alerting. Losing the Azure-native managed-identity / Key Vault / Application Insights wiring that's central to the learning goal of this project. Defer indefinitely.

**Non-Postgres options (DynamoDB, MongoDB, PlanetScale).** Loses Prisma's typed query API in its strongest form, loses pgvector, loses Postgres full-text search, loses `Prisma.sql` for the few raw-SQL escape hatches we'll want. The schema is relational; the access patterns are relational; the right tool is a relational database.
