# ADR-0001: Use Next.js App Router

## Status

Accepted

## Context

We need a web application framework. The project is a server-rendered, data-driven application with authentication, database access, and user-generated content. Key constraints:

- Single developer, so framework overhead should be low
- TypeScript required
- shadcn/ui is a hard constraint (per CLAUDE.md tech stack), and shadcn targets Next.js as its primary integration
- Must support server-side session validation (can't expose database to the browser)
- Deployment target is Azure Container Apps — a Docker container, not Vercel

We also had to choose between Next.js's two routing systems: the App Router (current) and the Pages Router (legacy).

## Decision

**Next.js 16, App Router.** Specifically: `create-next-app@latest` with `--app --no-src-dir --typescript --tailwind`.

## Consequences

**What this enables:**
- React Server Components: database queries run on the server, result HTML is sent to browser. No API layer needed for page data.
- Server actions: form submissions and mutations go server-side without writing route handlers.
- shadcn/ui works as designed — components, CLI, documentation all assume Next.js App Router.
- Turbopack dev server (default in v16) for fast iteration.

**What this forecloses:**
- Pages Router patterns (getServerSideProps, getStaticProps, API routes as primary data layer). We won't use these — not because they're wrong, but because mixing router paradigms in one app causes confusion.
- Vercel hosting as a drop-in option. We're deploying to Azure Container Apps. The app runs fine as a standard Node.js server (`next start`); we just don't get Vercel's edge functions or automatic image CDN.

**Operational burden added:**
- We need to understand the server/client component boundary. Mistakes here (using hooks in server components, exposing secrets through client components) are runtime errors, not compile errors.
- Next.js 16 renamed `middleware.ts` to `proxy.ts`. Any documentation or tutorial written before mid-2025 that references `middleware.ts` is slightly wrong for our setup.

**New risks:**
- Auth.js v5 + Next.js 16 compatibility is not officially documented (open issue #13302). The integration works in practice; we accept this risk to avoid future upgrade debt. If Auth.js v5 releases stable with explicit Next.js 16 support, this risk is retired.

## Alternatives considered

**Next.js Pages Router:** Still supported and stable. Would work. We chose App Router because: (a) it's where Next.js's development focus is, (b) React Server Components are a significant capability we want to learn, and (c) Pages Router patterns (getServerSideProps etc.) are increasingly legacy knowledge.

**Remix:** Strong server-first model, similar philosophy. Reasons not chosen: smaller ecosystem, shadcn doesn't have a first-class Remix integration, and the team (solo) is already learning the Next.js stack. Not a wrong choice — a different project context might prefer it.

**SvelteKit:** Different language (Svelte vs React), different mental model. Not aligned with the "become functional at modern React" goal.

**Express/Fastify + React SPA:** Separate backend and frontend. More architectural complexity, requires running two processes, requires a separate API layer for everything. No upside at v1 scale.

**Django/Rails:** Requires learning a second language/ecosystem in parallel. The goal is depth on the modern TypeScript stack. Ruled out on scope grounds.
