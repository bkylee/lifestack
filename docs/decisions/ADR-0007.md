# ADR-0007: NextAuth (Auth.js v5) for Authentication

## Status

Accepted

## Context

The application needs user authentication with Google and GitHub OAuth. Key constraints:

- OAuth has security requirements (state validation, CSRF, token handling) where mistakes cause account takeover vulnerabilities
- Sessions need to be database-backed so they can be revoked and survive restarts
- The Prisma adapter must integrate cleanly — Auth.js v5 has `@auth/prisma-adapter` as a first-class integration
- We're on Next.js 16, which renamed `middleware.ts` to `proxy.ts` — the auth library must support this

## Decision

**Auth.js v5** (`next-auth@beta`), configured with:
- `@auth/prisma-adapter` for database-backed sessions
- Google and GitHub OAuth providers
- `proxy.ts` with `runtime = "nodejs"` for Next.js 16 compatibility
- No split config — Node.js runtime allows direct database access in the proxy layer

## Consequences

**What this enables:**
- OAuth with Google and GitHub handled end-to-end by the library
- Sessions stored in Postgres `Session` table — revocable server-side
- `auth()` function available in any server component or server action
- CSRF protection, token rotation, and session expiry handled by the library

**What this forecloses:**
- Custom auth flows without explicit discussion (per CLAUDE.md security requirements)
- Easy swap to a different auth provider — the Prisma schema and session handling are Auth.js-specific

**Operational burden added:**
- `AUTH_SECRET` must be rotated if compromised — existing sessions invalidate on rotation
- `next-auth@beta` is not stable; API may change before v5 release

**New risks:**
- Auth.js v5 + Next.js 16 compatibility is not officially documented (open issue #13302). Works in practice. Risk accepted to avoid pinning to Next.js 15.

## Alternatives considered

**Lucia Auth:** Lower-level auth library — closer to building OAuth yourself, with typed session primitives. More control, smaller abstraction. Ruled out because: Auth.js has a mature Prisma adapter, larger ecosystem, and more documentation. Lucia requires more custom code for OAuth flows that Auth.js handles automatically.

**Clerk:** Hosted authentication service. Extremely fast to set up — UI components, user management dashboard, and webhooks included. Ruled out because: vendor lock-in (user data lives in Clerk's infrastructure, not our database), cost at scale (per-MAU pricing), and it removes a significant learning opportunity — understanding OAuth and session management is part of the architectural learning goal for this project.

**Auth0:** Similar to Clerk — hosted service, mature ecosystem, well-documented. Same reasons for ruling out: vendor lock-in, cost at scale, and the learning goal favors self-hosted auth.

**Custom OAuth implementation:** Full control, no library dependencies. Ruled out because OAuth has subtle security requirements (PKCE, state parameter, token validation) that are easy to implement incorrectly. The cost of a mistake is account takeover. Libraries that are used by tens of thousands of projects have had these edge cases found and fixed.
