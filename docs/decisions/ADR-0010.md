# ADR-0010: ACR Basic (not Premium) for v1

## Status

Accepted — 2026-05-10.

## Context

Lifestack needs a private container registry to hold the Next.js image that Container Apps pulls on deploy and scale-out. Azure Container Registry has three SKUs that differ on price, storage, and a set of capabilities concentrated in Premium.

Constraints:

- **$100/month subscription budget cap** (`infra/environments/prod/budget.tf`).
- **Single operator, one region** — no immediate need for geo-replication, signed image enforcement, or per-repository scope tokens.
- **The `privatelink.azurecr.io` private DNS zone was already provisioned in Step 2.3**, anticipating an eventual move to Premium with a Private Endpoint. Today the zone sits dormant.

| SKU | Cost | Included storage | Private Endpoint | Geo-replication | Content trust | Retention policy | Scope tokens |
|---|---|---|---|---|---|---|---|
| Basic | $5/mo | 10 GB | ❌ | ❌ | ❌ | ❌ | ❌ |
| Standard | $20/mo | 100 GB | ❌ | ❌ | ❌ | ❌ | ❌ |
| Premium | $50/mo | 500 GB | ✅ | ✅ | ✅ | ✅ | ✅ |

## Decision

Use **ACR Basic** in v1, with `admin_enabled = false` and `anonymous_pull_enabled = false` so every pull/push authenticates via AAD. Public network access stays enabled (the only mode Basic supports), but the security boundary lives in AAD/RBAC: the registry rejects all unauthenticated requests, and Container Apps will pull via managed identity + `AcrPull` (wired in Step 2.6).

Keep the `privatelink.azurecr.io` DNS zone deployed and linked to the VNet so a Premium upgrade is one resource away.

## Consequences

**What this enables:**

- ~$5/month registry cost. The whole v1 budget stays under $100/mo at idle.
- Same access-control posture as Premium for RBAC/authentication purposes — no admin user, no anonymous pulls, all access through AAD.
- Standard Docker/OCI tooling continues to work unchanged: `az acr login`, `docker push`, `docker pull`.

**What this forecloses (until we upgrade):**

- **No Private Endpoint.** Pull traffic from Container Apps to ACR egresses to the public ACR endpoint, even though both resources are in the same Azure region. AAD-token-gated, but not network-isolated. Defense-in-depth gap, not an access-control gap.
- **No geo-replication.** A single-region outage breaks new deploys (existing containers keep running on their last-pulled image). v1's single-region target makes this irrelevant.
- **No retention policy.** Old, untagged images accumulate. Mitigation: a scheduled GitHub Actions job to prune by age, written when CI/CD lands in Step 2.6. Without that script we'd consume Basic's 10 GB allowance in ~2.5 months at ~10 merges/month × ~400 MB.
- **No content trust.** Images aren't cryptographically signed at push time and verified at pull time. Not currently part of our threat model.
- **No scope tokens.** Can't issue per-repository tokens. Only relevant if we'd want to give a third party limited push access to one repository — we don't.

**Operational burden:**

- Periodic pruning of old images (automated in Step 2.6) until we either upgrade or accept the storage cost overage.
- Documentation reminder that "public ACR endpoint" doesn't mean "public images" — every pull is auth-gated.

**New risks:**

- A leaked AAD token with `AcrPull` could be used from anywhere on the public internet (with Premium + PE, the same token would also need network reachability to the VNet). Mitigation: short-lived managed-identity tokens, RBAC scoped to the registry resource, no human users granted `AcrPull` on prod.
- Hitting Basic's 10 GB storage cap if pruning lapses. Trigger to escalate: `az acr show-usage` reports > 8 GB.

## Triggers to revisit (move to Premium)

1. **Compliance / security audit** demands network-isolated image pulls.
2. **Multi-region deployment** requires geo-replicated images.
3. **Signed image enforcement** becomes part of the deploy gate (content trust).
4. **Per-repository scoped access** for an external integration.
5. **Storage repeatedly exceeding Basic's 10 GB** even after retention tuning.

The Premium upgrade is in-place — change the SKU, add a Private Endpoint resource pointing into `snet-pe-prod`, and the existing `privatelink.azurecr.io` zone takes over name resolution. No image migration, no name change.

## Alternatives considered

**ACR Premium with Private Endpoint** (full v2 posture today). $50/mo plus PE compute time ≈ $58/mo. Adds network isolation and unlocks the full Premium feature surface. Rejected because it pushes the v1 budget over $100/mo and the access-control posture is already correct under Basic.

**ACR Standard.** $20/mo, 100 GB. Buys storage and throughput we don't need; doesn't unlock any v1-relevant capability (PE/geo/etc. are all Premium-only). Strictly worse than Basic for v1 economics, with no learning advantage.

**ACR Premium for one month, then downgrade to Basic.** Considered. Lets us wire up the PE pattern end-to-end and document it, then back off the recurring cost. Rejected because the destroy-and-recreate path loses pushed images, and the Premium → Basic SKU change is supported but tricky to roll back cleanly. We can revisit when Container Apps is live in Step 2.6 and CI/CD images exist to test against.

**GitHub Container Registry.** Free at our scale. Cross-tenant auth (GitHub OIDC → Azure) adds a second identity surface to reason about. Loses the "everything in one Azure tenant" learning value that's central to this project. Defer indefinitely.

**Docker Hub.** Different trust boundary, anonymous-pull rate limits have caused outages industry-wide. Not on the table for a production-style stack.

**Self-hosted registry on the existing Container Apps env.** Free in marginal compute, but registry storage, garbage collection, and HA become our problem. Saved $5/month, paid in hours of operations. Not the right trade.
